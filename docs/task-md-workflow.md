# TASK.md 運用ガイド

この文書は、特定repoに依存しない形で `TASK.md` + `AGENTS.md` を使って開発作業を渡すための運用ルールをまとめたもの。

目的は、会話側で仕様・優先順位・Git運用を決め、実装担当（Codex等）が勝手に再解釈せず、そのまま実装できる状態を作ること。

---

## 1. 基本構成

各repoのルートに最低限次を置く。

```text
AGENTS.md
TASK.md
docs/
```

役割は次の通り。

### AGENTS.md

repo共通の「作業ルール」。

- TASK.mdを読む
- Git運用を勝手に再判定しない
- repo誤指定を安全に検出する
- test / commit / push / PR / 最終報告の流れ
- main直pushとbranch作業の基準
- merge権限や完了後の扱い

などを定義する。

### TASK.md

その時点で実装する「最新の作業指示書」。

- 種別
- 目的
- Git運用
- 背景
- 仕様
- 触らない範囲
- test
- 完了条件
- 最終報告

を書く。

TASK.mdは長期仕様書ではない。
長期仕様は `docs/` へ置き、TASK.mdは「次に実装する仕事」に集中させる。

---

## 2. 重要: タスク種別とGit運用は別軸

この2つを混同しない。

### タスク種別

作業の目的・文脈の分類。

```text
新規タスク
既存タスクへの追加
既存タスクへの追加修正
既存タスクの再実行
既存タスクの完了処理
```

### Git運用

変更をどうGitへ載せるか。

```text
main直接push
branch + PR
```

たとえば、

- merge済みのUIを同じ目的で微調整する → 既存タスクへの追加
- 新しい予測指標を追加する → 新規タスク

となり得る。

「merge済みだから新規タスク」ではない。

逆に、新しい目的なのに追加扱いすると、古い前提・完了条件・Git運用を引きずる危険がある。

---

## 3. タスク種別の判断

### 新規タスク

目的が変わる、別の成果物になる、または独立した検収単位になる作業。

例:

- 新機能追加
- 新しい予測指標
- UIカードの全面再設計
- 新しいworkflow
- 別データ構造の導入

### 既存タスクへの追加

同じ目的の中で要求を追加する場合。

例:

- 同じUI改善の中でアイコンをさらに大きくする
- 同じカード改善でラベルを短くする
- 同じ機能の受入条件を追加する

### 既存タスクへの追加修正

実装結果を見て、同じ目的の設計・式・挙動を修正する場合。

例:

- validation結果を見て式を作り直す
- 実機確認後に配置を調整する

### 既存タスクの再実行

仕様は変えず、失敗・未完了・環境問題などで同じ仕事をもう一度実行する場合。

### 既存タスクの完了処理

PR merge、cleanup、完了確認など、実装後の締め作業。

---

## 4. Git運用の決定者

実装担当にGit運用を決めさせない。

作業開始前にレビュー担当/設計担当が変更内容を見て、

```text
main直接push
```

または

```text
branch + PR
```

をTASK.mdへ明記する。

実装担当はその指定をそのまま実行する。

TASK.mdにGit運用が無い場合は、推測せず停止する。

---

## 5. main直接pushの目安

次のような変更はmain直接push向き。

- 文言変更
- docs更新
- 表示位置、余白、サイズ、色
- 局所的なUI調整
- 実機だけで良否を判断しやすい変更
- 既存ロジックへ影響しない軽微な修正
- revertしやすい変更

main直pushではPRを作らない。

push後に実機・実画面で検収する。

---

## 6. branch + PRの目安

次はbranch作業向き。

- 内部ロジック
- 予測式・計算式
- データ構造
- 保存形式
- API / 認証 / 権限
- CI / workflow / build設定
- 大規模refactor
- 複数機能に波及する変更
- 実験的変更
- 影響範囲が不明
- 複数日にまたがる可能性が高い作業

迷った場合はbranch。

branch作業ではPRを作り、mainへmergeする前にコード検収する。

## 7. TASK.md 推奨テンプレート

```markdown
# TASK.md

## 種別

新規タスク

# タスク名

## Git運用

main直接push
または
branch作業

理由:
- ...

## 背景

なぜこの作業をするか。

## 目的

今回どの状態を作るか。

## 1. 仕様

...

## 2. 仕様

...

## 触らないもの

- ...
- ...

## テスト

- ...
- ...
- git diff --check

## 完了条件

- ...
- ...

## 最後の報告

- Git運用
- branch名（branchの場合）
- commit SHA
- PR番号（branchの場合）
- test/build結果
- 変更ファイル
- 残課題
```

ポイントは、「やること」だけでなく「触らないもの」を書くこと。

実装担当は善意で周辺まで直しがちなので、スコープ境界を明記する。

---

## 8. AGENTS.md 推奨フロー

実装担当が起動されたら、概ね次の順番で処理する。

```text
1. 対象repoを確認
2. AGENTS.mdを読む
3. TASK.mdを読む
4. TASK.mdのGit運用を確認
5. 実装
6. test / lint / build
7. commit
8. push
9. branch作業ならPR作成
10. 最終報告
```

TASK.mdが無い、またはGit運用が無い場合は停止する。

---

## 9. repo誤指定の自動補正

複数repoを並行して扱う場合、作業開始前に次を照合する。

- 現在開いているrepo
- repo直下のTASK.md
- repo直下のAGENTS.md
- `git remote get-url origin`
- TASK.mdに対象repo明記がある場合はその記載

次の条件なら自動補正してよい。

- TASK.md / AGENTS.md / originが同じrepoを示す
- ユーザー指定だけが違う
- 正しいrepo候補が一意

補正時は明示する。

```text
repo指定を <誤指定repo> から <補正後repo> に補正しました。
```

次の場合は補正しない。

- TASK.mdとoriginが食い違う
- 候補repoが複数
- 証拠が矛盾
- 別projectへ誤適用する危険がある

この場合は停止して差異だけ報告する。

## 10. 他repoへコピーするときの注意

AGENTS.mdにrepo固有URLを直書きしない。

悪い例:

```bash
git remote add origin https://github.com/example/project-a.git
```

これを別repoへコピーすると誤pushの原因になる。

汎用版では、

```text
originが無い場合は、TASK.mdまたは明示された対象repoから
正しいremoteを一意に特定できる場合のみ設定する。
一意に特定できない場合は停止する。
```

とする。

repo固有のbuild手順、deployment、SDK制約などは、
共通AGENTS.mdへ混ぜすぎず、各repo側の追加セクションとして持たせる。

---

## 11. 追加指示の入れ方

同じタスクの途中で仕様追加が出た場合、TASK.mdへ追記してよい。

ただし長くなりすぎたり、目的が変わった場合はTASK.mdを新しいタスクで置き換える。

判断基準:

```text
同じ目的 → 追加/追加修正
別の目的 → 新規タスク
```

過去の実装経緯を永久にTASK.mdへ残す必要はない。

完了後に残す価値がある知識はdocsへ移す。

---

## 12. 会話側の運用

作業を依頼するときは、ユーザーへ必ず分類を明示する。

例:

```text
今回は新規タスクです。
Git運用はbranch + PRです。
```

または:

```text
今回は既存タスクへの追加修正です。
Git運用はmain直接pushのままです。
```

これにより、

- 仕様文脈
- Git運用
- merge状態

を混同しにくくなる。

---

## 13. merge運用

branch作業では、実装担当自身にmergeまで自動実行させない運用が安全。

推奨:

```text
実装担当
→ branch push + PR作成まで

レビュー担当
→ diff / test / validation確認

ユーザー
→ merge承認

レビュー担当
→ merge実行
```

承認用の合言葉を決めてもよい。

例:

```text
まじおk
```

ただしこれはプロジェクト固有の会話ルールなので、必須ではない。

## 14. 最終報告フォーマット

### main直接push

```text
Git運用: main直接push
commit: <SHA>

変更:
- ...

test:
- ...

実機確認:
- ...
```

### branch + PR

```text
Git運用: branch
branch: <name>
commit: <SHA>
PR: #<number>

変更:
- ...

test:
- ...

残課題:
- ...
```

## 15. この方式の狙い

この運用で分離したいのは次の4つ。

```text
何を作るか       → TASK.md
どう働くか       → AGENTS.md
長期仕様         → docs/
どうGitへ載せるか → TASK.md内のGit運用
```

実装担当へ判断を丸投げせず、
一方で細かな実装方法まで会話側で固定しすぎない。

仕様判断・Git判断・実装・検収を分離することで、
複数repoや複数AI担当を跨いでも同じ流れを再利用できる。
